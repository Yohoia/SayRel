执行摘要

SayRel 已具备录音中 ASR、最终结果元数据和本地编辑学习。真实缺口主要是润写效果验收、卡顿时的兜底、上下文细化与上屏成功确认。竞品机制可作参考，但静态结构不能证明质量，也不能直接决定修改优先级。

核实修订版 · 2026-10-24：本版修正了三路竞速、协议缺失、函数调用适用范围、词典替换、partial 追加和 IME 防御等判断。详细核实记录见 四款竞品对比文档核实记录。本文建议不等于已确认的故障原因。

架构有不同路径，不是互斥的两类产品

Wispr Flow、Typeless 的客户端主要调用厂商提供的语音服务；Voiskey 把较多编排放在 Go 原生层；闪电说同时存在自带 API Key 与会员后端路径；SpeakMore 是开源批量实现，直出/混合/离线三模式并列、离线完全本机。SayRel 当前以用户选定的 ASR 和 LLM 为主。服务端、原生编排与供应商聚合可以共存。

请求域名、协议字段与客户端处理逻辑可核对。是否自训模型、是否联合训练、线上使用哪条路径以及实际质量，不能由这些证据推出。

当前应优先核实什么

  • 润写效果：“请求成功”不代表“整理达标”。应核对同一次请求的档位、prompt 版本、ASR 原文、模型正文与实际插入文字。结构化输出不能自动解决原样返回。
  • 转写兜底：live 失败后以同一选定模型重处理完整录音；没有通用的定时竞速或跨供应商容灾。batch-fallback 是逻辑路径名，不保证改用 HTTP。
  • 上屏确认：native helper 的主路径已使用剪贴板与 Cmd+V，但发送按键后返回 0，尚未证明目标应用实际接收了文字。
  • 安全扩展：光标数据尚未进入润写上下文；显式替换规则、按应用风格与学习锚点可按需求补充。普通词典不能直接当作纠错替换表。

架构路径与可比范围

比较时应分别看服务归属、客户端编排位置与后处理方式。不能只按“自有后端 / 聚合供应商”二选一。

厂商服务与原生编排

  • Wispr Flow 的请求和返回协议包含转写、格式化、上下文及风格。它的客户端还执行条件性替换与排版处理，并非只把结果贴回。
  • Typeless 在 renderer 编排实时与 HTTP 通道，主进程负责上下文、隐私、存储和部分网络转发。服务端模型与 prompt 未恢复。
  • Voiskey 的录音、网络和润写较多在 Go 原生层，恢复的前端也包含编辑学习与功能逻辑。“原生负责”不等于“已证明本地模型推理”。
  • SpeakMore 是开源批量实现：直出（音频模型一跳）、混合（转写→整理）、离线（本机 ONNX）三模式并列。它把「识别方式」做成独立维度，与「任务」正交，且显式拒绝流式——与 SayRel 的 live 流式是同一功能的两条相反路线。
  • Baseten 域名是服务承载线索，不是厂商自有域名或自训模型的证明。端点与 pipeline 字段也不能证明联合训练、共享模型状态或质量收益。

自带 API Key 与会员后端可以并存

  • 闪电说有供应商目录、自带 key、会员服务与原生编排。会员日志说明后端按 revision 构建 prompt；不能据此覆盖自带 key 路径。
  • SayRel 分开选择转写与润写模型，并承担鉴权、采样、协议收口、失败处理和插入。模型选择、prompt、上下文与交付可靠性都会影响体验。
  • 容灾可以是同模型重试、定时备用通道或显式选择第二供应商。是否竞速应根据失败类型、费用、隐私和实测收益决定。
本报告能比较客户端已观察到的机制，不能从架构推导谁的润写更好。SayRel 应先验证实际整理效果，再按故障证据选择机制。

转写（语音 → 文本）链路逐产品

Wispr Flow —— 一条 gRPC 双向流 + 四态消息

→

要点：

  • 一条流、四种请求消息（init/payload/context/commit），服务端一边收音频一边回实时状态——同一条流暴露转写与格式化进度，但不能据此证明内部模型联合训练或同时推理。
  • 状态是进度比值不是布尔：formatter 进度追上 transcriber 才算 Formatted，天然表达「识别完了但润写还没完」的中间态。
  • 回退是竞速不是串行：服务端已接收音频比客户端已发音频落后 >2s 时，可触发 gRPC / Baseten HTTP 竞速。该路径受 GrpcHttpRace 开关和音频时长限制，并等待录音结束；其他重试路径不等于三路同时并发。

Typeless —— 实时流为主，6 秒后 HTTP 兜底竞速

录音renderer 用 16 kHz AudioContext + Worklet 采集，三项系统 DSP 全关
→
实时上传约每 1 s 切块，走 wss://…/ws/rt_voice_flow；二进制容器未确认
→
部分转写服务端逐块回 transcription{text,chunk_index}，浮条追加显示
→
松键end_audio（带 7 段延迟打点）+ 立刻后台并行压缩整段音频
→

→
收敛先到者胜，落败方 abort；paywall 中断会话；清本地音频

要点：主进程部分可在 reference/typeless/readable/main.index.deobf.js 按行号核对；实时通道在 renderer 的 1uHho0F_.js（class Lf）与 juYOhWy9.mjs（状态机与消息组装），见 reference/typeless/README.md §4。

  • 上一版结论「没有流式」是错的，原因可复现：当时只反混淆了主进程，而主进程确实不认识转写——实时链路整条在 renderer。补上 renderer 后可见完整协议：客户端 7 种消息（start_audio/set_audio_chunk_info/replace_audio_context/set_selected_text/set_mode_config/end_audio/ping），服务端 17 种（含 transcription、refine_completed、process_mode、audio_session_ending）。
  • 兜底不是「失败后重试」，而是「提前算好 + 定时器竞速」：松键瞬间就启动整段压缩，压缩与 6 s 计时器并行；到点直接发 HTTP。WS 赢了就 abort 掉 HTTP（同一个 abortId），并用 race:winner 打点记录赢家。SayRel 目前是「实时失败了才回退」，中间有一段失败发现延迟。
  • 弱网是一等公民：一旦判定弱网，后续块不再上传，整条会话直接退化为只等 HTTP；开始录音时最多等 5 s 建连，超时即按弱网起步。
  • 部分转写按索引片段管理：transcription 带 chunk_index。SayRel 适配器已将多种协议合成累计快照；两种接口语义不同，不应把其 UI 直接改为追加，否则可能重复文字。
  • 最终原文接口未确认：实时通道可获得转写分片，成品消息给润写文字。当前证据未见独立权威的最终 ASR 原文及仅润写重试接口；不能推导客户端完全没有原文或绝对无法实现对照。
  • mode 决定服务端 prompt：voice_transcript→transcript、voice_command→ask_anything、voice_translation→translation；parameters 只在 command/translation 下带 selected_text / output_language。
  • 采集端把「不加工」写死：echoCancellation/noiseSuppression/autoGainControl 全部显式 false；开始提示音按设备动态延迟（同设备 1200 ms、AirPods 300 ms），避免提示音被自己录进去。
  • 音频编码有降级链：buffer 模式失败（native -5）→ 缓冲区加倍重试 2 次 → 整体退到文件模式（临时 WAV → 转 Ogg）。存在上述编码降级分支，不能保证所有编码故障都不阻断听写。

Voiskey：Go 原生编排与前端状态、学习逻辑

启动闸门权限→麦克风→弱网→系统可达性，逐项过
→
采集Go 原生，带 500ms 预热 / 250ms 稳定 / 3s 无输入检测
→

→

→

要点：

  • 音频 LRU 缓存：HasAudioCache/RetrySpeechRecognition/WriteAudioCacheWAV/DeleteAudioCache——存在缓存重识别、导出与 FlushPreGateAudio 入口；可重试范围、保留期与离线续传的完整语义未确认，不能保证任意过去录音随时可用。
  • 两套网络口径分离：公网弱网探测（5s TCP，>500ms 弱网 / ≤300ms 恢复，带迟滞）与系统可达性（1.5s）互不覆盖，避免状态打架卡死。
  • 空语音与断线分离：空结果看峰值/静音比例，断线看 failType=ws_heartbeat_timeout，两者走完全不同的重试/文案路径。

0.8.0 原生层补充（src/asr/cloud/*，全部为字符串级观察）：

  • 实时与批量是两份实现，不是一份代码的开关：openai_realtime_asr.rs 与 openai_audio_asr.rs 并存；ElevenLabs 同一模块里既有 wss://…/speech-to-text/realtime 也有 [ElevenLabsASR] Starting batch ASR transcription。SayRel 也已有不同的 HTTP/WS 处理分支，部分能力选择依赖模型名。应明确模型形态与回退兼容性，不能由模块数量直接判断可靠性。
  • ws_proxy.rs：观察到代理模块名与相关日志；实际支持的系统代理类型、默认策略和每条路径尚需原生函数体或请求验证。
  • net_diag.rs：独立的网络诊断模块，把「连不上」当一等公民。
  • 观察到 16 kHz 采样相关常量；字符串出现次数和未命中其他数值不能证明所有路径统一使用该采样率。
  • 重试有专用入口：retry_voice_input / [RetryTranscription]，且归一化之后才判空（[ASR] Text is empty after normalization, skipping injection）——SayRel 是在 ASR 层判空。

要点：源码在 reference/speakmore/upstream/（提交 7bf2124），分析见 reference/speakmore/README.md。

  • 纯批量、显式拒绝流式：asr/cloud/vendors.mjs 写明「听写说完就要出字，等不起轮询，也不必为一整段录音开流」。这与 SayRel 的 live 实时流是同一功能的两条相反路线，各有论证。
  • 三模式平级：native（录音→收音频模型直出成品）/ local（转写→纯文字模型整理）/ private（本机 ONNX 转写、不上传、无 key）。三个实现装成同一接口 warmUp/prepare/refine，服务端只认接口。
  • 本地 ASR 子进程隔离：模型在 fork 子进程跑（约 2 GB 常驻），崩了只丢一次转写；GPU 起不来自动换 CPU。长录音按模型 maxSeconds 在音量最静点切开、静音段跳过。
  • 预热与提示词缓存：warmUp 先把「第一次慢 2 倍」从用户第一句话上挪走（3.4–4.1 s → 1.7–1.9 s）；Gemini 有提示词缓存 prepare。

润写（文本 → 成文）链路逐产品

Wispr Flow：服务端结果与客户端确定性处理

  • 服务协议暴露 FORMAT、StyleConfig 和编辑强度。general_style 按 other/personal/work/email 分类，另有 Slack、签名等配置。服务端实际模型与 prompt 未知。
  • 客户端 bundle 第 166817 行附近包含全小写、整段片段触发、词典/替换规则、专名大小写和应用特化。规则确定地处理匹配项，不代表能纠正所有识别错误或保证所有词典词出现。
  • 独立 Polish/Transform 路径调用 /llm/polish_text，使用选中文字和指令，通过 ShowDiff 展示结果。它与听写后的自动润写不是同一条流程。

Voiskey：原生润写与编辑后的词典学习

  • SpeechResultModel 保留润写后 text 与原始 asrText。Go 润写有约 45 s 等待上限。两层文本可作对照，学习还依赖插入后的用户编辑与上下文跟踪。
  • computeAfter 根据 caret prefix/suffix 切出区间，再结合句级 LCP/LCS、头尾锚点与 1000 字限制收缩。恢复代码还处理 placeholder、输入清空和句数差异。
  • 学习涉及持久化、撤销、翻译场景过滤与 IME 防御。原生未恢复部分及服务端抽词的实际效果仍未知。

闪电说：协议路由、会员策略与候选输出契约

  • 目录和原生字符串显示多个 LLM 协议及角色配置。SayRel 也已支持 openai-chat、openai-responses、anthropic、gemini、ollama、azure-openai，不缺 /responses。独立助手角色属于产品范围扩展。
  • 观察：存在 text_correction、corrected_text、tool calls 与函数调用开关。推断：部分配置通过工具参数取正文。没有函数体或真实请求证明默认强制方式、完整 schema 与适用供应商；配置修复日志还显示它与自定义 prompt 有关联。
  • 会员路径日志说明后端按 Voice-Input-Revision 构建 system prompt。自带 key 路径有 base_prompt_chars、full_prompt_chars 和发送 prompt 的日志，其基准 prompt 来源仍未知。字符串扫描未命中不证明 prompt 不存在。
  • 前端可确认 raw/light/strong，默认 light。日志有 organize_level，不能断言所有模式都只在服务端实现档位。
  • 配置与历史 UI 显示归一化规则、去句末句号，以及 original_text、normalized_text、ai_corrected_text。完整执行顺序未取得；既有分析在 AI 前后顺序上存在冲突。字段展示次序不等于执行次序。
  • 日志支持关闭/AI 失败时回原文，并有鉴权过期事件线索；前端默认超时为 15 s。没有真实请求统计证明所有失败分支行为。
结构化输出约束的是结果形状，不保证模型真正改写、保留全部事实或不拒绝。若引入，必须验证正文并由客户端计算 changed；不能将它作为“深整理无变化”的已证实修复。

Typeless：服务端润写与细粒度上下文

  • 恢复的上下文包含 device_environment、active_application、text_insertion_point、context_metadata，涉及 app/窗口、选中文字、光标前后文、输入区周边和采集质量。字段与消费点可核对，服务端使用方式未知。
  • 已见可见文本 10,000 字符/500 ms 与周边文本 1,000+1,000 字符/500 ms 等预算，以及 app/URL 黑名单和加密信封。加密保护传输/存储封装，不意味着服务端无法读取上下文。
  • WS 可返回转写分片与润写完成消息；HTTP 返回成品文本。目前未找到独立权威的最终 ASR 原文或仅润写重试接口。不能写成客户端完全拿不到转写文字。

Typeless 编辑学习与 SayRel 的取舍

  • 插入后检查目标与已插入文字，进入约 15 秒空闲跟踪窗口；白名单中的真实按键可续期。切换输入框、清空、Enter 与超时会结束跟踪。15 秒是可重置的空闲窗口，不是已证实的总时长上限。
  • 只比较前 1000 字符，长度低于原文 20%、删除超过 50% 或增删超过 2 倍等条件会过滤大幅改写；随后通过 /user/traits 上传改前改后文本与上下文，返回词典项。
  • SayRel 已有本地 diff、50%/2 倍长度过滤和至少 60% 不变文本约束，默认关闭且需要用户确认。两者隐私、召回与误报取舍不同，未经评测不能断言服务端必然更强。普通同义改写也不一定应成为词典项。

SpeakMore：一份调好的润色 prompt + 确定性清洗

  • 零参数单一 prompt，与 SayRel 的 polishLevel×writingStyle 多参数相反。作者用同一批 60 条真实录音跑 12 遍（720 条成品）对照原版 Typeless 的 2853 条成品调出来，每条规则带「改了之后命中怎么变」的实测数字。
  • 静音哨兵 NO_SPEECH_MARK="<无人声>"：让模型没人声时输出固定标记而不是「什么都不输出」，因为实测静音让它空输出会编出「好的」「你觉得呢？」；服务端见标记换空串。
  • 混合版 prompt 三处加强（模型看不到录音只看到转写）：先列「原文常见的错」让模型按上下文改；原文包在 <原文> 标签里，说清那是「要整理的内容」不是「对你说的话」；分点规则更重（照搬原生写法时原版分了点的 16 条只分 4 条）。
  • 确定性清洗（textFromModelOutput）：LEAKED_PREFIX 正则剥掉成品前的多余外文词、OpenCC 繁转简、去句末句号（只删最后一个，中间各段句号保留）。
  • 夹时间戳整次重试：成品含 \d{1,2}:\d{2} 就整次重来一遍，不直接删（防误删真钟点）。

SayRel 现状精读（源码级）

以下描述当前工作区已有能力，不是待补清单。具体结果仍依赖所选模型、配置与网络。

采集、实时与完整录音重试

  • src/renderer/floating-bar/audio.ts 以 16 kHz 为目标，启用 echoCancellation/noiseSuppression/autoGainControl；Worklet 按 2048 样本交付，失败退 ScriptProcessor。
  • recordingMachine.ts:131 在录音开始时调用 live ASR，后续 PCM 同时缓存并推送。supportsLiveTranscription 选择兼容模型，不是所有 ASR 都实时。qwen3-asr-flash 等批量模型仍在松键后识别。
  • realtimeTransport.ts 有 15 s 连接确认、360 s 会话、45 s final 超时，以及发送队列与 socket 缓冲合计 15 s 音频积压保护；没有通用服务端 ACK/lag 反馈。
  • providers/index.ts 已包含 OpenAI 批量、StepFun、MiMo、audio-chat、local-whisper、ElevenLabs REST 等不同路径；Qwen 与其他实时协议在 realtime.ts 中另有处理。
  • transcription.ts:47 起在 live 失败后重调同一选定模型，输入为完整录音。可能使用 HTTP，也可能重新通过 WS 发送；path=batch-fallback 不代表独立批量 API。
  • AsrOutcome 已区分 final/empty/failed，记录会话、请求、供应商/模型、路径及时间信息。当前不伪造词典命中、分段置信度或时间戳。

润写与上下文

  • ASR 完成后独立调用选定的 writing 模型。recordingMachine.ts:539 起将档位、风格、标点、词典与上下文传入请求，失败落回原文并允许只重试润写。未选择 writing 模型则跳过；历史记录已区分未配置、失败回退、成功未改动与已改动，并可查看原文及按当前设置重新整理。
  • refinementPrompt.ts 有 preservation、raw/light/strong、style 等策略，strong 额外加入 dictationPolicy。保留事实与引用，不等于必须保留口头绕述；档位是否产生预期差异须靠输出案例验证。
  • chat.ts 支持 6 种协议，包含 /responses；按协议检查完成状态、拒绝、工具调用及空结果。OpenAI chat/Azure 分支使用 temperature 0.2，并非所有协议都发送同一温度。DeepSeek auto 的听写请求使用低 reasoning effort。
  • contextCapture.ts 与 prompts.ts 提供 app、选中文字、输入框预览和可见文本等，并屏蔽安全字段。光标位置、区间和 IME 数据已用于本地学习，尚未进入润写上下文；缺输入区类型、周边内容和采集质量。
  • 词典同时用于 ASR 提示与润写 preferred_spellings，不是强制替换表。postprocess.ts 仅做换行、空白和尾随空格处理，不删除解释性前缀。响应合法但附带解释的正文仍可能被接受。
  • RefinementOutcome 已记录 completed/skipped/fallback，completed 有 changed、模型、prompt 版本和耗时。错误 message 有区别，但缺稳定分类；日志与新元数据已记录实际请求档位、风格和标点设置，便于复现。

上屏、编辑学习与历史

  • insertion.ts 默认首次尝试加两次重试，间隔 120 ms。swift/InputHelper.swift:37 内部已经保存剪贴板、写文本、模拟 Cmd+V 并延迟恢复，返回 0 前未读回确认。显式失败才走手动粘贴提示。
  • insertRichText 接口存在但主链路未用；富文本是特定编辑器的格式能力，不是纯文本失败的通用兜底。
  • dictionaryLearning.ts 在上屏前取快照，250 ms 首次检查，随后每秒采样，固定总窗口 15 s；编辑稳定约 1.5 s 或 Enter 后生成候选。目标变化、secure 或 IME 会停止跟踪。
  • editLearning.ts 校验前后缀、目标一致、UTF-16 光标、1000 字上限、改写幅度和词形；候选上限 50、10 分钟过期。用户确认才入词典，5 s 内可撤销，仍保持本地学习。
  • 历史保留 transcript/refinedText/finalEditedText 等层；finalEditedText 是有界编辑快照，不保证等于最终发送内容。历史重识别依赖可用音频，处理阶段才写占位；仅加占位记录无法恢复崩溃丢失的内存 PCM。
“深整理没有变化”应先区分未配置、请求失败回退、成功但未改动，以及插入了错误层文本。已有接口与本地测试通过，不构成真实润写质量验收。

差距分析 · 转写

P0 表示已证实的正确性风险或当前阻塞验收项；P1 是可靠性与边界完善；P2 是按需求评估。未进行竞品线上性能测试，阈值不能直接照搬。

P1缺少有界的定时兜底，而非缺少实时能力

现状：录音中 live 已实现。当前仅在 live 明确失败后重处理完整录音，不竞速。
证据与边界：Typeless 有默认约 6 s 触发 HTTP 的路径；Wispr 有受开关与时长限制的 gRPC/Baseten HTTP 竞速。触发备用请求不等于该秒数内完成。
建议：先确认所选模型是否支持录音中处理，再评估松键后提前准备完整音频并在等待超预算时启动兼容备用路径。必须处理空结果、错误、会话取消和失败分支，不能只取第一个 settled Promise。记录赢家、耗时及可能重复费用。

P2跨供应商容灾与服务端滞后反馈需单独设计

现状：没有备选供应商选择；已有发送积压保护，但没有统一的服务端接收进度。
证据与边界：Wispr 的 lag 是已发送音频时长减服务端确认时长，不是“上一次 partial 距今”。静音、停顿与仅返回 final 的模型可能长期无 partial。
建议：先用协议 ACK、socket 状态、发送积压与 final 等待预算观测问题。跨供应商上传必须用户明确配置和授权，区分计费/隐私成本；不将无 partial 自动判为宕机。

P1润写缺光标前后文，但 native 已有部分采集能力

现状：当前 reference_context 只有输入框预览和选中等字段。光标与 IME 已在本地学习快照中使用。
证据与边界：Wispr/Voiskey/Typeless 的恢复材料有不同粒度的光标与周边上下文；不能据此证明上传更多就一定更好。
建议：复用已有采集，区分本地学习许可与上传上下文许可。加入有界 before/after、输入区类型与采集质量，secure/IME/目标变化时安全降级；不要默认上传完整输入框。

P1统一代理策略和诊断不足，具体故障仍需复现

现状：undici WebSocket 未显式接入统一代理/连通性诊断；具体代理环境行为未验证。
证据与边界：闪电说有 ws_proxy.rs/net_diag.rs 字符串线索，不能只凭模块名确认所有系统代理类型均支持。Electron session 代理不自动等于 Node 网络栈代理。
建议：以实际 WS 握手、TLS、鉴权和网络错误分类为依据，分别验证 HTTP/WS 的代理行为。普通 HEAD 成功不证明 WS 可用，失败也不能直接判 ASR 不可用；探测不应阻塞录音。

P1模型能力元数据需比文件拆分更明确

现状：实时和批量已有不同的 HTTP/WS 实现，但部分路由依赖模型名和协议条件。部分完整录音重试仍复用 WS。
证据与边界：OpenAI 的实时/批量在模型中已区分，ElevenLabs REST 与 WS 也已分支。闪电说文件名体现模块划分，不证明“必须每种形态一个类”。
建议：显式描述模型是否支持 live、完整录音和可兼容回退，并验证模型/端点组合。按协议边界拆分代码，而不是为文件数量或类数量重构。

P2编码开销需测量后决定是否改为增量编码

现状：部分路径在松键后编码；live 成功且不存音频可跳过。是否造成明显等待尚未按录音长度测量。
证据与边界：Typeless 恢复了连续编码和整段转码路径。接口存在及 worker 配置不代表所有通道都使用同一编码方式，实时二进制容器仍有未知。
建议：先测 encodingMs、持久化及模型耗时，再选择 worker 或 native 增量编码。若用 WebCodecs，要验证 Electron 版本、执行上下文、编码器与容器支持，不假定 AudioWorklet 直接可用。

P1跨会话恢复依赖保存的音频

现状：内存帧与当前 retryInput 不构成持久缓存；已有历史重试，但依赖可用 audioLocalPath。
证据与边界：Voiskey 有缓存、重识别及导出入口，覆盖范围受缓存保留影响；单有 DB 占位不等于可恢复音频。
建议：若确需崩溃/离线恢复，将临时缓存与长期归档分别设计，明确用户许可、容量、保留期、清理与恢复原子性。不能在“关闭保存音频”后静默持久化。

P1展示真实阶段，不伪造转写/润写进度比值

现状：已有 phase、partial 和分段耗时；历史已显示未配置、失败回退和成功未改动，真实模型未改动的语义原因仍需文本对照。
证据与边界：Wispr 有服务端 transcriber/formatter 进度；SayRel 的普通 LLM 请求没有可验证的中间百分比。
建议：区分连接、识别、润写、插入，并保留已识别文本预览。历史状态与重新整理入口已补齐；后续评估浮条阶段提示，不把累计 partial 再追加。

P2会话上限与供应商元数据是能力选择

现状：录音上限 5 分钟；已有 final/empty/failed 元数据，缺统一分段时间戳、置信度和词典归因。
证据与边界：Voiskey usedDictList 与 Wispr 增删统计不是同一种数据。请求里的 context.terms、hotwords 或 vocabulary 只证明传入提示，不证明返回命中归因。
建议：时长按模型能力和实测成本配置。仅在响应实际提供字段时映射；本地匹配只能称“输出包含词典词”，不能伪装成供应商确认命中。

差距分析 · 润写

P0先建立真实润写效果验收

现状：档位、风格和 prompt 已接通；本地契约测试不能判断真实模型是否把口语整理成预期成文。用户反馈“深整理无变化”仍需同次请求对照定位。
证据与边界：completed/changed 只能证明完成和文本差异。长度变短也不证明保留了事实、否定、引用及意图。结构化输出可以合法返回原文。
建议：记录脱敏的请求档位、模型、prompt 版本、结果状态与耗时。用用户同意保留的失败例及合成用例覆盖填充词、改口、重复、多任务、混合语言、数字与否定；比较原文/模型正文/插入文本，明确三档各自允许的编辑幅度。

P1缺任务级正文契约，但已有协议完整性检查

现状：已有响应 schema、完成状态、拒绝和空值检查；没有工具/结构化正文模式，也没有删除解释性前缀的清洗规则。
证据与边界：闪电说存在函数调用路径线索，适用范围与强制方式尚未知。服务端返回成品字段也不证明内部杜绝格式错误。
建议：按模型能力验证工具或结构化输出模式，校验正文和失败类型，保留纯文本路径。changed 由客户端计算，避免为 notes 增加无用输出；以真实错误率证明收益，不宣称必然解决润写力度。

P1缺显式替换与片段规则，不是把词典再替换一遍

现状：词典已用于 ASR 与润写提示，但仅保存正确词，缺错误写法/触发词到输出的明确映射。
证据与边界：Wispr 有条件性确定性处理；闪电说有规则配置和三层文本字段，执行顺序未证实。精确词边界不解决词义歧义或中文分词问题。
建议：分开建模词典、显式替换、片段与排版。规则需用户确认，可预览、禁用与撤销。决定各规则在润写前还是后执行，并记录实际文本层；若允许正则，限制规则数量/输入长度并防止灾难性回溯，不盲目推导纠错映射。

P1全局风格可扩展为按应用覆盖

现状：polishLevel 与 writingStyle 是全局设置。
证据与边界：Wispr 有应用类别风格；Voiskey 有场景与应用映射。场景数量不等于效果更好。
建议：按 bundleId 给可选覆盖，仍服从用户编辑预算与隐私设置。先验证邮件、聊天、笔记与代码场景，再扩展目录。

P1词典学习可提高边界召回，但不能删掉已有防御

现状：已有目标、secure、IME、前后缀、1000 字、长度比例和至少 60% 不变文本过滤；尚无进一步锚点收缩，窗口是固定 15 s。
证据与边界：Voiskey 采用多步锚点，Typeless 有按键续期。两者更复杂不等于对本地词典学习必然更准。
建议：以具体漏学/误学例验证锚点，边界不唯一时放弃。可评估空闲续期加总时长上限；保留确认、撤销与本地计算，不把同义改写默认当词典项。

P2独立选中文字润写与 diff 属于范围扩展

现状：已有语音编辑和桌面白名单指令，但无完整的选中、润写、diff、确认替换流程。
证据与边界：Wispr 有独立 Polish/Transform 和 ShowDiff。它不等于日常听写润写。
建议：需求明确时复用 interactiveCard，先展示 before/after，再确认目标与替换范围；无需为解决自动润写问题先扩展此功能。

差距分析 · 上屏

P0返回成功不等于目标应用已写入

现状：native helper 主路径是剪贴板 + Cmd+V，发出事件后返回 0。JS 默认首次加两次重试，但未读回确认，因此目标未接收时可能被当成成功。
证据与边界：见 swift/InputHelper.swift:37 与 insertion.ts。Voiskey 有延迟校验线索；Wispr 有 PasteOutcome。它们不能证明仅比字符数就足够可靠。
建议：确认目标身份与插入区间，尽可能对比有界文本；无法验证时返回 unknown，而非假成功。仅比较字符数会漏掉等长错误。结果不明时避免自动重复粘贴，保留用户可控的手动恢复。

P1剪贴板保存与恢复需要可观测结果

现状：helper 已保存并延迟恢复剪贴板，JS 侧没有恢复结果。
证据与边界：现有代码可直接核对，不仅是注释宣称。异步恢复还需考虑用户或其他进程在这期间修改剪贴板。
建议：记录实际方法、写入/恢复结果与耗时；恢复前校验归属或 changeCount，避免覆盖用户新复制的内容。保留多类型、多项目数据的语义。

P2富文本是场景能力，不是通用失败回退

现状：insertRichText 已存在，但主链路只使用普通文本。
证据与边界：Wispr/Typeless 有 HTML 相关接口。支持富文本不代表编辑器会接受，也不证明它能修复纯文本插入失败。
建议：仅在用户需要且目标支持时生成并交付安全 HTML，同时保留纯文本；与上屏成功确认分开实施。

优先级建议

本表是针对当前项目和用户反馈的工程判断，不是竞品功能的客观排名。P0 的验收缺口不等于根因已查明。

优先级事项验收要求
P0定位深整理效果，建立语义验收同次请求对照档位、prompt、原文、模型结果、插入文本；区分跳过/回退/未改动，检查事实保留与口语整理。
P0上屏结果可信目标不接收、部分写入和等长错误不能报 verified 成功；不可验证需 unknown，不盲目重贴。
P1定时完整录音兜底与模型能力声明对支持组合测试卡住、早失败、空结果、取消及备用失败；计时触发不冒充总耗时上界。
P1按能力试验结构化正文输出兼容模型确实减少格式错误，拒绝/截断仍被识别，质量不回退；保留纯文本路径。
P1显式替换规则与文本层只应用用户授权映射，预览/关闭/撤销可用，规则有资源限制，原始文本可对照。
P1光标上下文、代理诊断、剪贴板恢复各自验证隐私开关、预算、网络栈和剪贴板所有权；不得为新增功能扩大静默上传或覆盖用户内容。
P1学习召回、应用风格与临时缓存分别以真实漏学、场景需求和恢复需求决定；保留安全过滤、用户确认和清理策略。
P2跨供应商竞速、连续编码、富文本、独立 diff有明确需求与实测收益后实施，验证计费/隐私、格式兼容及目标写入安全。
推荐顺序：先定位“深整理无变化”并补上屏确认，再验证实时卡住时的有界兜底。输出契约、替换规则和上下文增强各自解决不同问题，不能代替真实润写效果验收，也不应先按竞品功能数量重构。
