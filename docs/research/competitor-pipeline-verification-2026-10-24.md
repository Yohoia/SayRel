# 四款竞品对比文档核实记录

核实日期：2026-10-24。

核实对象：`docs/competitor-pipeline-comparison.html`，对照当前 SayRel 工作区，以及 `reference/` 中已恢复的发布产物、协议、符号和分析材料。未修改原报告或业务代码，未调用真实供应商接口，未重新反编译竞品。下文描述的是这些本地版本，不代表竞品所有版本或线上配置。

## 结论

报告识别了多项真实缺口，但不能直接当作实施计划。主要问题是：把条件性路径写成默认行为，把静态字符串推断写成事实，把不同协议的实现方式当成优劣，以及把输出格式稳定性与语义润写质量混为一谈。

尤其是“深整理没有明显变化”，不能从这份报告直接归因于缺少函数调用或确定性后处理。原样返回可以是合法的模型正文；结构化输出也可以合法返回相同正文。需要比较同一次请求的档位、prompt 版本、ASR 原文、模型结果与实际插入文本。

## 需要更正的结论

### 1. Wispr 不是已证实的 HTTP / Baseten / OpenAI 三路同时竞速

- 原文：HTML 第 187、276、465 行。
- 核实：`reference/wisprflow/readable/main.index.pretty.js:142954` 的 `startParallelHttpFallback` 是 gRPC 与 Baseten HTTP 竞速；受 `GrpcHttpRace` 功能开关控制，等待 `recordingFinishedPromise`，且会跳过超过时长阈值的音频。
- 第 143439 行附近确实存在“已发送音频时长减服务端已接收时长”的 lag 判断。其他 HTTP/OpenAI 回退路径存在，不等于同一时刻三路并发。
- 应改为：存在受开关和时长限制的 gRPC / HTTP 双通道竞速，另有其他重试路径。不能据此要求 SayRel 先实现三供应商竞速。

### 2. 闪电说函数调用机制有证据，但适用范围和强制方式尚未证实

- 原文：HTML 第 188、383、562 行。
- 核实：原生字符串存在 `text_correction`、`corrected_text`、`tool_calls`、`arguments` 及函数调用配置项，也存在“custom prompt disabled but FC was still true”的配置修复记录。可支持“存在函数调用输出路径”，不能证明所有支持工具的供应商默认强制走它。
- 证据：`reference/shandianshuo/evidence/native-strings.txt`；`reference/shandianshuo/pipeline-deep-analysis.md:122` 的推断及证据边界说明。没有函数体或真实请求可确认完整分支与 schema。
- 应改为：候选实现机制，适用配置和供应商范围待确认。摘要不应把正文的“推断”升级为事实。
- 结构化输出可减少正文与解释混杂，但不能保证不拒绝、不截断、不原样返回，更不能保证整理质量。`changed` 应由客户端实际比较，不应信任模型自报。

### 3. SayRel 缺少 `/responses`、StepFun、MiMo 的说法错误

- 原文：HTML 第 382、634 行；同文第 441 行又列出了 `openai-responses`，前后冲突。
- 核实：`src/main/services/providers/chat.ts:83` 已有 `/responses` 请求和对应响应解析；`src/main/services/providers/index.ts:82` 有 StepFun；第 107 行有 MiMo。
- 应改为：这些协议已实现；是否需要继续扩充能力或验证兼容性，应另列，不能按“尚未接入”排期。

### 4. SayRel 不是靠字符串规则擦掉模型解释，也不是完全不验证输出

- 原文：HTML 第 561 行。
- 核实：`src/main/services/providers/postprocess.ts:4` 只做换行和空白规整，没有删除“以下是润色后的文本”的规则。`chat.ts:33` 起检查完成状态、工具结果、拒绝等；`transport.ts:53` 起拒绝空文本。
- `RefinementOutcome` 确实没有结构化的错误分类枚举，但 fallback 的 message 能保留不同失败原因，不能写成“完全无法区分”。
- 应改为：已有响应协议和完整性检查，缺少任务级正文契约，以及稳定的错误分类。解释性正文可能被当作合法文本接受，而不是一定被清洗失败后丢弃。

### 5. 普通词典不等于确定性替换规则，且闪电说的处理顺序未证实

- 原文：HTML 第 189、570–572 行。
- 核实：SayRel 确实没有用户替换规则或片段展开层，但词典不只用于润写：`providers/prompts.ts:17` 和实时协议适配器也把词典用作 ASR 提示。
- `src/main/db/schema.ts:71` 的词典只保存 `word` 等字段，没有“错误写法 → 正确写法”映射。仅有正确词，无法安全推导应替换哪个错误词。加词边界也解决不了语义歧义，尤其是中文。
- Wispr 确有客户端确定性处理，见其 bundle 第 166817 行附近；只能保证明确规则匹配后的行为，不能保证所有词典词或识别错误“100% 命中”。
- 闪电说的规则配置和三层文本展示有证据，但没有原生函数体证明完整处理顺序；其分析文件在第 3.1 与 3.6 节分别写了归一化在 AI 之前、之后，彼此矛盾。
- 应改为：将词典提示、显式替换映射、片段展开、排版规则分别建模；规则顺序是 SayRel 的待设计项，不是已证实的竞品标准。

### 6. partial 不能统一从替换改成追加

- 原文：HTML 第 645 行。
- 核实：`providers/realtime.ts:83` 已将 OpenAI/Qwen delta 合成累计文本；Fun-ASR 按句子 ID 合成快照；Soniox 合成 final 与非 final token。协调器收到的多种 partial 已经是完整快照。
- 如果 UI 再直接追加，会把“你”及后续“你好”显示成“你你好”。
- 应改为：协议适配器负责把增量、累计快照或带索引片段归一到同一种预览语义。Typeless 的 `chunk_index` 模式不能直接移植成通用追加。

### 7. 传入热词不能证明供应商返回了词典命中

- 原文：HTML 第 549 行。
- 核实：`context.terms` 等请求字段能证明发送了提示，不能证明返回协议提供“本次因词典而识别正确”的归因数据。Wispr 的字数增删统计也不等于热词命中记录。
- 应改为：只有实际响应有对应字段时才回传；本地输出与词典的匹配只能命名为“输出包含词典词”，不能称为供应商确认的命中或学习效果。

### 8. 词典学习并非没有 IME 或大幅改写防御

- 原文：HTML 第 414、485、650–651 行附近的差距与迁移建议。
- 核实：`swift/InputHelper.swift:113` 起读光标位置和输入框内容，第 153 行读 IME marked range。`src/shared/editLearning.ts:4` 拒绝组字状态；第 26 行已有长度比例过滤，第 29 行要求至少 60% 文本不变；同时有目标一致性、前后缀边界和长度限制。
- 真正缺口：这些光标数据用于本地学习，尚未进入润写的 `AudioContextSnapshot/reference_context`；没有 Voiskey 那种进一步的锚点收缩。
- 固定 15 秒窗口和 Typeless 的按键续期确实不同，但属于召回率与隐私的取舍，不能单凭时长判断错误。增加续期应保留总时长上限。
- “同义替换抽词必然弱于服务端”未经对照评测；普通同义改写也不一定应该进入用户词典。

### 9. `batch-fallback` 不保证切换到了 HTTP 批量服务

- 原文：HTML 第 206、429、464 行附近的概括。
- 核实：`src/main/services/transcription.ts:47` 起在 live 失败后重新调用同一选定模型的适配器。`providers/realtime.ts:417` 起只有部分模型走 HTTP；其他模型仍可能在录音结束后重新用 WS 发送完整音频。
- 应改为：同供应商、完整录音重试；网络传输形态取决于具体模型。路径名不是传输保证。
- “只有硬超时”也需限定：`realtimeTransport.ts:127` 已有 15 秒发送积压检测，但没有 Wispr 的服务端已接收时长 ACK/lag 反馈。
- 缺少最后一次 partial 不能直接判定服务端落后：静音、停顿及仅返回 final 的模型都可能无 partial。

### 10. 上屏缺口成立，但原生 helper 本身已经使用剪贴板

- 原文：HTML 第 190、445、605 行附近。
- 核实：`src/main/services/insertion.ts:30` 默认首次尝试加两次重试。`swift/InputHelper.swift:37` 的正常路径就是保存剪贴板、写入文字、模拟 Cmd+V，再延迟恢复，并非已证实成功的 AX 写入。
- 更具体的缺口是：helper 发出事件后直接返回 0；创建并发送了按键事件，不等于目标应用接受了文字。主进程因此可能误报插入成功，无法触发重试。
- 应改为：保留“缺上屏成功确认”的判断，明确验证目标身份和插入区间；不能只检查字符数，等长错误或部分写入可能漏检，也不能在结果不明时盲目再次粘贴。
- 富文本是可选的场景能力，不是纯文本写入失败的通用修复。

### 11. 闪电说 prompt 全在服务端的结论范围过大

- 原文：HTML 第 384–385 行。
- 核实：会员路径的日志支持“服务端按 revision 构建 prompt”。但原生字符串也明确有 `base_prompt_chars`、`full_prompt_chars`、`organize_level`、`dictionary_chars` 和“VoiceInput system prompt sent to provider”。
- 应改为：会员路径如此；自带 key 路径会组装并发送 prompt，基准 prompt 的来源仍未知。CJK 字符串扫描未命中不能证明没有英文、压缩、动态拼接或下发的 prompt。
- 因此闪电说不是严格的“仅 BYOK 聚合”架构；自有服务与 BYOK 可以并存。“自有后端”也不能证明自训模型、联合训练或特定质量收益。

### 12. Typeless 没有最终原文接口，不等于客户端拿不到任何原文

- 原文：HTML 第 301 行。
- 核实：同文确认实时 `transcription{text, chunk_index}`，因此客户端能获取部分转写。`reference/typeless/README.md:128` 也列出了该消息。
- 应改为：当前证据没有独立、权威的最终 ASR 原文或仅润写重试接口。分片可以形成过程预览，但未证实等同最终原文；不能把“未找到接口”写成绝对不可能。

## 基本成立的缺口

以下是对 SayRel 当前实现的描述；不代表每项都应列为 P0：

| 项目 | 核实结果 |
| --- | --- |
| 录音中 ASR | 已实现，`recordingMachine.ts:131` 在录音开始时建 live session；只有兼容模型启用。选择 `qwen3-asr-flash` 等批量模型仍在录音后识别，不是全项目没有 realtime。 |
| 最终 ASR 元数据 | 已有 `final/empty/failed`、会话与请求 ID、路径等。缺分段时间戳和词典归因不能推导为“缺最终协议”。 |
| 回退 | 同供应商、失败后触发；没有通用的定时竞速或备用供应商选择。 |
| 润写上下文 | 有 app、选中文本、输入框预览等；尚未提供光标前后对称文本及上下文采集质量。 |
| 确定性规则 | 没有独立的用户替换/片段规则层；不能用普通词典自动替换代替。 |
| 写作风格 | 只有全局档位和风格，没有按应用覆盖。 |
| 编辑学习 | 已有本地 diff、确认、撤销、隐私边界；缺进一步锚点收缩及可续期跟踪。 |
| 历史与音频 | 处理开始时才写占位；跨会话重识别依赖可用历史音频。录音中的内存 PCM 不具备崩溃恢复能力，单加 DB 占位也不能恢复它。 |
| 音频编码 | 当前是在录音后处理路径编码；是否构成可见性能瓶颈需要按录音长度、模型、是否存音频实测。 |
| 网络 | 当前实时 transport 未显式接入统一代理策略或独立诊断；企业代理下的具体失败仍需在对应网络复现，不能写成必然失败。 |
| 上屏 | 主链路使用纯文本，缺可靠的目标写入确认；已有富文本接口但未接入主链路。 |

## 对当前项目的优先级判断

1. **先定位真实润写效果。** 为同一次请求保留可选、脱敏的档位、prompt 版本与文本对照；明确展示“已整理但未改动 / 未配置模型 / 请求失败回退”。用中文填充词、改口、口头重复、多任务、引用、数字与否定等案例评测 raw/light/strong，而不是只检查请求里是否有这些字段。
2. **修复已证实的可靠性风险。** 优先补上屏结果确认，以及实时卡住时有界的完整录音兜底。计时器触发第二条请求不等于总耗时被限定在该秒数，还须考虑第二条请求时延、失败、费用及取消。
3. **按实测引入正文契约与显式规则。** 支持工具或结构化输出的模型可以分能力接入；保留不支持者的纯文本路径。替换规则应用户明确授权并可预览/禁用，不能猜测专名替换。
4. **再补上下文和学习召回。** 复用已有 native 光标/IME 数据，经过隐私开关和长度预算后进入润写；再评估应用风格、学习锚点与续期。
5. **跨供应商竞速、连续编码和后编辑 diff 按需求排期。** 它们是独立的成本与范围选择，不是“竞品有所以本项目必须 P0 补齐”。
